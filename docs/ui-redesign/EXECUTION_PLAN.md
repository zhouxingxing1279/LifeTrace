# LifeTrace 用户端 UI 重构与右键交互执行方案

> 文档状态：待执行  
> 适用范围：LifeTrace Tauri 桌面客户端用户端 UI  
> 技术栈：Tauri 2、React 19、TypeScript、Vite、Zustand、Lucide React  
> 设计基线：`design-system/life-trace/MASTER.md`  
> 更新日期：2026-08-07

---

## 1. 背景

当前用户端已经具备习惯、成长、健身、每日英语、笔记、记账、照片同步、本地加密相册、AI 和设置等模块，但界面仍存在明显的“网页后台”特征，尚未形成统一、成熟的桌面软件体验。

主要问题包括：

1. 页面长期显示过多辅助文字、说明文字和状态提示，用户难以快速识别核心任务。
2. 正文、辅助文字和局部组件字体偏小，连续使用时视觉负担较大。
3. 卡片、按钮、标签、提示和边框数量过多，页面被切割成大量碎片。
4. 页面级、卡片级和行级操作全部直接展示，操作密度过高。
5. 不同模块使用各自的 CSS 和交互模式，字号、间距、圆角、菜单和反馈方式不一致。
6. 缺少统一的右键菜单与 `···` 更多菜单体系，低频操作无法有效收纳。
7. 部分大组件同时承担布局、业务状态和交互逻辑，后续持续重构成本较高。

本次重构不只是调整颜色和圆角，而是重新建立用户端的信息层级、组件体系和桌面交互规范。

## 2. 重构目标

### 2.1 产品目标

用户打开任意页面后，应能快速明确：

1. 当前页面最重要的信息是什么。
2. 当前最需要执行的操作是什么。
3. 详细信息和低频操作从哪里打开。

最终界面应呈现为安静、克制、清晰、可长期使用的个人管理桌面软件，而不是由大量卡片和说明文字组成的数据后台。

### 2.2 可量化目标

重构完成后应满足：

- 常规可阅读文字不得小于 `14px`。
- `12px` 和 `13px` 仅用于图表刻度、快捷键、极短元数据等受限场景。
- 常驻辅助说明文字数量相比重构前减少至少 50%。
- 页面标题区最多包含 1 个主操作和 2 个次要操作。
- 普通列表行或卡片默认最多直接展示 1 个主要操作和 1 个 `···` 菜单入口。
- 所有业务对象的右键菜单与 `···` 菜单复用同一份 Action 定义。
- 删除、永久删除、清空和覆盖等危险操作必须二次确认。
- 右键菜单必须支持鼠标、键盘和屏幕边缘碰撞处理。
- 在 `1280×720`、`1440×900` 和 `1920×1080` 下均不存在核心内容遮挡或操作不可达。
- `npm test`、`npm run test:rust` 和现有业务测试全部通过。

### 2.3 非目标

本次重构不包含：

- 修改核心业务规则和数据模型。
- 一次性重写所有页面业务逻辑。
- 将项目迁移到新的前端框架。
- 引入完整的大型视觉组件库并替换全部现有组件。
- 强制让浏览器端和桌面端在第一阶段完全同步重构。
- 为了“视觉丰富”增加无实际价值的动画、渐变或装饰卡片。

## 3. 总体设计原则

### 3.1 任务优先

每个页面第一屏只突出当前状态、下一步行动和核心内容。说明、规则、来源、计算口径和历史细节默认后置。

### 3.2 渐进式展示

| 信息类型 | 展示方式 |
| --- | --- |
| 完成任务必须知道 | 常驻展示 |
| 需要时才查看 | Tooltip、Popover、详情抽屉、折叠区 |
| 操作结果反馈 | 自动消失的 Toast |
| 表单错误 | 紧邻对应字段展示 |

禁止把所有信息都用常驻小字放在页面上。

### 3.3 主操作可见，低频操作收纳

- 主操作保持直接可见。
- 编辑、复制、移动、归档、导出和删除等低频操作进入右键菜单或 `···` 菜单。
- 任何重要操作不得只存在于右键菜单中。
- 右键菜单与 `···` 菜单必须功能一致。

### 3.4 使用间距建立层级

优先通过字号、字重、间距和分隔线建立层级，减少卡片套卡片、大量边框、多层背景色、无意义阴影和重复标签。

### 3.5 桌面端优先

本方案以 Tauri 桌面客户端为主，支持右键菜单、快捷键、鼠标悬停、多选、批量操作、详情抽屉和分栏布局。不得使用 Electron 专有 API；系统文件操作通过现有 Tauri command 或 Tauri plugin 完成。

- `src/components/PhotoSyncDashboard.tsx`。

### 4.2 当前结构风险

1. 大组件同时承担导航、页面布局、状态和业务操作。
2. 多个 CSS 文件各自声明字体、间距、颜色和控件尺寸。
3. 相同交互可能在不同模块重复实现。
4. 如果直接逐页修改，容易产生新旧规范并存的问题。

因此必须先完成基础设计系统和公共交互层，再逐模块迁移。

## 5. 目标字体与尺寸体系

现有 `MASTER.md` 中部分正文和辅助字号偏小，本次需要同步修订设计系统文档和实际 CSS Token。

### 5.1 字体层级

| Token | 字号 / 行高 | 字重 | 使用范围 |
| --- | --- | --- | --- |
| `--font-page-title` | `24px / 32px` | 700 | 页面标题 |
| `--font-section-title` | `18px / 26px` | 600 | 主要区块标题 |
| `--font-card-title` | `16px / 24px` | 600 | 卡片、列表对象标题 |
| `--font-body` | `15px / 22px` | 400 | 正文、主要表格内容 |
| `--font-secondary` | `14px / 20px` | 400 | 时间、状态、次要信息 |
| `--font-caption` | `13px / 18px` | 400 | 短说明、字段补充 |
| `--font-micro` | `12px / 16px` | 400 | 图表刻度、快捷键等极少场景 |

禁止在业务组件中新增 `10px` 或 `11px` 字体。

### 5.2 控件尺寸

| 控件 | 建议尺寸 |
| --- | --- |
| 常规按钮高度 | `36px` |
| 主要按钮高度 | `40px` |
| 紧凑图标按钮 | `32px` |
| 输入框高度 | `38px` 或 `40px` |
| 侧边栏导航项 | `40px` 至 `44px` |
| 右键菜单项 | `36px` |
| 表格常规行高 | `44px` 至 `48px` |

### 5.3 间距体系

```css
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-5: 24px;
--space-6: 32px;
--space-7: 40px;
--space-8: 48px;
```

组件不得任意新增大量非标准间距。

## 7. 统一 Action 与右键菜单系统

### 7.1 Action 数据模型

右键菜单、`···` 菜单、快捷键和命令面板应尽量复用同一套 Action 定义。

```ts
export type ActionGroup =
  | "primary"
  | "related"
  | "organize"
  | "danger";

export interface AppAction<TContext = unknown> {
  id: string;
  label: string;
  icon?: React.ComponentType<{ size?: number }>;
  shortcut?: string;
  group?: ActionGroup;
  danger?: boolean;
  hidden?: boolean | ((context: TContext) => boolean);
  disabled?: boolean | ((context: TContext) => boolean);
  children?: AppAction<TContext>[];
  execute: (context: TContext) => void | Promise<void>;
}
```

要求：

- 菜单本身不得包含业务判断。
- 各模块在自己的 `actions.ts` 中创建 Action。
- `ContextMenu` 与 `MoreMenu` 只负责渲染和触发。
- 危险 Action 必须调用统一 `ConfirmDialog`。
- Action 执行成功或失败后通过统一 Toast 反馈。

### 7.2 菜单视觉规范

- 宽度：`180px` 至 `220px`。
- 菜单项高度：`36px`。
- 字号：`14px`。
- 图标：`16px`。
- 菜单分组最多使用 3 条分隔线。
- 危险操作放在底部，并使用克制的危险色文字。
- 禁用项必须可识别，但不能通过低对比度导致不可读。
- 快捷键显示在右侧。
- 超过 8 个操作时使用二级菜单或重新精简。

### 7.3 交互要求

必须支持：

1. 鼠标右键在指针附近打开。
2. 靠近窗口边缘时自动翻转或修正位置。
3. 点击菜单外关闭。
4. `Esc` 关闭。
5. `ArrowUp`、`ArrowDown`、`Home`、`End` 移动焦点。
6. `Enter` 或 `Space` 执行。
7. 子菜单支持左右方向键。
8. 菜单打开时目标对象保持选中高亮。
9. 多选后显示批量操作菜单。
10. 空白区域显示当前页面级菜单。
11. 输入框、编辑器和可编辑文本区域不得破坏复制、剪切、粘贴、全选等标准操作。

### 7.4 技术实现决策

阶段 0 创建一份简短 ADR，比较成熟 Headless UI Primitive 与 React Portal 自研方案。默认原则：

- 不引入完整视觉组件库。
- 可以引入体积可控的 Headless Primitive。
- 视觉样式必须完全由 LifeTrace Token 控制。
- 业务 Action 模型不得依赖第三方组件 API。

### 7.5 Tauri 与系统能力边界

- 习惯、笔记、流水、文章、训练和照片等业务对象使用前端自绘菜单。
- “在文件夹中显示”“打开本地文件”等系统操作通过 Tauri command 或插件完成。
- 不得使用 Electron `Menu`、`shell`、`ipcRenderer` 等 API。
- 对本地加密相册，右键菜单、任务栏预览、系统最近文件和日志不得泄露缩略图、文件名或敏感路径。

## 8. 各模块右键操作矩阵

### 8.1 习惯与成长

对象右键：标记完成 / 取消完成、补记、查看详情、编辑、置顶、调整顺序、暂停、归档、删除。

记录右键：编辑记录、修改完成时间、添加感受、复制记录、删除记录。

### 8.2 健身

查看训练详情、继续相同训练、编辑记录、添加备注、导出训练数据、复制训练摘要、删除。

### 8.3 每日英语

文章右键：打开阅读、标记已读 / 未读、收藏 / 取消收藏、重新阅读、查看阅读笔记、导出笔记、删除记录。

选中文本后使用浮动工具栏：高亮、翻译、添加笔记、复制。

已高亮文本右键：修改高亮颜色、添加或编辑笔记、复制、取消高亮。

### 8.4 记账

单条流水：查看详情、编辑交易、修改分类、修改账户、添加备注、标记为转账、标记为不计入统计、查找相似流水、删除。

多选流水：批量修改分类、批量修改账户、批量添加标签、批量排除统计、批量删除。

### 8.5 笔记

打开、快速预览、重命名、复制、置顶、收藏、移动到文件夹、导出、归档、删除。

### 8.6 普通相册与照片同步

打开、查看详情、旋转、收藏、移动到相册、复制文件、在文件夹中显示、移入回收站。

### 8.7 本地加密相册

打开、查看详情、移出加密相册、永久删除。

安全限制：

- 未解锁时不得注册照片级右键操作。
- 锁定后立即清除当前选中对象和菜单上下文。
- 禁止把明文路径写入 Toast 或普通日志。

### 8.8 侧边栏和空白区域

侧边栏模块：在当前窗口打开、固定 / 取消固定、调整顺序、隐藏非核心模块。

页面空白区域：新建当前模块对象、调整排序、切换紧凑 / 舒适视图、刷新当前模块。

“今日”和“设置”等核心入口不得被隐藏。

## 9. 分阶段执行计划

### 阶段 0：基线审计与重构边界

任务：

1. 对全部用户端页面截图，建立重构前视觉基线。
2. 扫描硬编码字号、间距、圆角、颜色和 z-index。
3. 统计低于 `14px` 的文字使用点和常驻提示文字。
4. 统计重复菜单、按钮、Toast、Dialog、Drawer 和 Tooltip 实现。
5. 确认桌面端和浏览器端共用代码的边界。
6. 创建右键菜单技术选型 ADR。
7. 建立 `uiRedesignV2` 功能开关。

产物：

- `docs/ui-redesign/BASELINE_AUDIT.md`。
- `docs/ui-redesign/ADR_CONTEXT_MENU.md`。
- 重构前页面截图或测试附件。
- 可切换的新旧 UI 功能开关。

验收：所有主要页面均有基线记录，且未开始无边界的大面积样式覆盖。

### 阶段 1：设计系统与 Token 重建

任务：

1. 更新 `design-system/life-trace/MASTER.md` 的字体规范。
2. 新增 `app/tokens.css`。
3. 将颜色、字体、间距、圆角、阴影、控件高度和 z-index 转为 Token。
4. 在 `app/globals.css` 中建立统一字体和基础可读性规则。
5. 建立 `Button`、`IconButton`、`PageHeader`、`SectionHeader` 等基础组件。
6. 禁止新增低于 `12px` 的字体，并审查所有低于 `14px` 的使用。

验收：新组件不再硬编码视觉值，页面正文默认达到 `15px / 22px`，文档与 Token 一致。

### 阶段 2：应用壳层与页面布局

任务：

1. 拆分 `HengXuShell.tsx` 中的壳层、侧边栏、标题栏和页面容器。
2. 统一侧边栏宽度、导航项尺寸、折叠状态和激活状态。
3. 所有一级页面接入统一 `PageHeader`。
4. 页面主内容不再默认包裹一层大卡片。
5. 建立统一内容最大宽度、页面内边距和滚动区域。
6. 清理重复标题、宣传式副标题和长期说明文字。
7. 建立紧凑视图和舒适视图的密度 Token。

验收：一级页面的标题、操作区和内容起始位置一致，且不影响现有模块切换。

### 阶段 3：公共交互基础设施

任务：

1. 实现统一 Action 模型。
2. 实现 `ActionMenu`、`ContextMenu` 和 `MoreMenu`。
3. 实现菜单定位、碰撞处理、焦点管理和快捷键。
4. 实现统一 `ConfirmDialog`。
5. 升级 Toast，支持成功、警告、错误和进度状态。
6. 实现统一 `Tooltip`、`Popover` 和 `Drawer`。
7. 编写公共交互组件单元测试。

验收：同一 Action 可同时用于右键和 `···` 菜单；菜单支持完整键盘操作；输入框和 Tiptap 编辑器标准右键能力不被破坏。

### 阶段 4：试点模块重构

第一试点为习惯 / 成长，第二试点为笔记。

习惯 / 成长：

- 将卡片式堆叠改为以“今天要做什么”为中心的列表。
- 直接保留完成操作。
- 编辑、补记、暂停、归档和删除进入 Action 菜单。
- 将规则说明迁移到 Tooltip 或详情抽屉。

笔记：

- 采用列表 / 编辑器 / 详情的清晰分栏。
- 将行内多个按钮收纳到 `···` 和右键菜单。
- 保留快速新建、搜索和当前编辑状态。
- 验证 Tiptap 与自定义右键菜单的边界。

验收：两个试点模块功能无回退，不使用右键时仍可通过 `···` 找到全部低频操作。

### 阶段 5：其余模块迁移

按以下顺序迁移：

1. 记账。
2. 每日英语。
3. 健身。
4. 普通相册与照片同步。
5. 本地加密相册。
6. AI、设置及其他辅助页面。

模块重点：

- 记账使用表格或高密度列表，详情进入抽屉，并完成多选和批量右键操作。
- 每日英语正文宽度控制在约 `680px` 至 `760px`，正文使用 `17px` 至 `18px`，选中文字后显示浮动工具栏。
- 健身第一屏只展示本周训练、最近训练、下一计划和关键趋势。
- 相册统一缩略图、选中状态、多选、批量移动和回收站。
- 加密相册锁定后清除敏感组件、菜单上下文和选中状态。

### 阶段 6：清理、测试与发布

任务：

1. 删除废弃 CSS、重复组件和高风险 `!important`。
2. 将超大组件继续拆分为壳层、展示组件和业务 Hook。
3. 检查全部小字、常驻提示、右键菜单、更多菜单和快捷键。
4. 完成视觉回归、键盘可访问性和不同分辨率测试。
5. 默认开启新 UI，并保留一个版本周期的回退开关。
6. 稳定后删除旧 UI 和功能开关。

验收：不存在新旧设计系统长期混用、同一功能两套 Action、仅能通过右键访问的重要操作或未经确认的危险操作。

1. 页面标题是否唯一。

9. 键盘是否可完成核心操作。
10. 缩放到 125% 和 150% 后是否仍可用。

## 11. 回滚策略

### 11.1 功能开关

重构期间使用 `uiRedesignV2` 控制新旧壳层或模块 UI：

- 默认只在开发环境开启。
- 模块迁移完成后逐个开放。
- 发布验证稳定后改为默认开启。
- 保留旧 UI 一个版本周期后删除。

### 11.2 数据安全

UI 重构不得直接修改持久化结构。Action 必须调用现有 Service、Store 或 Tauri command，禁止在菜单组件中直接操作数据库。

### 11.3 提交粒度

按 Design Token、壳层布局、Action 与菜单基础设施、单个模块迁移、测试与旧代码清理分别提交。每个提交必须可构建、可运行、可单独回退。

---

## 12. 执行规则

后续 Agent 执行本方案时必须遵守：

1. 修改前阅读 `design-system/life-trace/MASTER.md` 和本文件。
2. 不得一次性重写整个用户端。
3. 每个阶段先建立公共能力，再迁移业务模块。
4. 不得用更多小字解释不清晰的交互。
5. 不得通过隐藏功能解决布局问题。
6. 不得让右键菜单成为重要功能的唯一入口。
7. 不得在业务组件中创建独立 Toast、Dialog、Drawer 或菜单体系。
8. 不得引入 Electron API。
9. 不得在加密相册日志和提示中泄露敏感信息。
10. 每完成一个模块，更新实施状态、测试结果和剩余风险。

## 14. 最终界面特征

重构后的 LifeTrace 用户端应具备：

- 清晰稳定的桌面应用骨架。
- 足够大的正文和控件字体。
- 少量、明确、可预测的页面操作。
- 以列表、表格和详情抽屉替代大量碎片卡片。
- 完整的右键、更多菜单、快捷键和多选能力。
- 操作反馈及时，但不会长期占据页面。
- 不依赖说明文字也能理解的交互。
- 普通模块保持高效，加密模块保持严格安全边界。

> 默认只展示用户此刻需要的信息，其余信息在用户需要时再出现。

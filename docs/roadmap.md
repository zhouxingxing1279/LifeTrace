# LifeTrace 完整产品与开发路线图

> 更新日期：2026-08-09  
> 用途：将 LifeTrace 的基础架构、多端应用、业务模块、任务与邮件、轻量 AI 管家及日常使用闭环拆分为可独立设计、开发和验收的 GitHub Epic。  
> 组织方式：每个大任务包含目标、子任务、依赖关系和验收标准，可继续拆分为 Issue、技术设计和迭代版本。  
> 产品原则：**本地优先、离线可用、云端保存完整副本、统一领域服务、渐进式重构、AI 受控执行、客户端与云端全链路可观测。**  
> Android 应用规划：财务、笔记、英语、习惯可独立成 App；**健身不制作独立 App，也不在 LifeTrace 中重复建设完整训练模块，仅接入训记数据用于汇总、时间线和分析。**

## 1. 产品目标

LifeTrace 的最终定位不是单纯的数据记录软件，也不是复杂的自主 Agent，而是：

> **一个本地优先、跨端同步、能够聚合个人生活数据，并由轻量 AI 管家提供自然语言操作入口的个人生活系统。**

整体结构：

```text
Windows 本地应用
├── SQLite 本地数据库
├── 离线完整可用
└── 增量同步客户端

Android 独立应用
├── LifeTrace Finance
├── LifeTrace Notes
├── LifeTrace English
└── LifeTrace Habits

Web / PWA
├── 访问云端完整副本
├── 响应式页面
└── 有限离线能力

LifeTrace Cloud
├── Rust / Axum API
├── PostgreSQL
├── 对象存储
├── 邮件同步 Worker
├── 推送服务
└── AI 调用协调

轻量 AI 管家
├── 了解已确认的个人信息和偏好
├── 简单聊天
├── 查询 LifeTrace 数据
└── 调用受控业务工具
```

## 2. AI 管家边界

AI 管家需要做到：

- 读取与当前请求相关的个人资料和偏好
- 进行普通、简短的连续对话
- 识别自然语言中的操作意图
- 调用 LifeTrace 注册工具
- 查询账单、任务、笔记、邮件等业务数据
- 返回真实执行结果
- 对写操作提供确认、审计和撤销

第一阶段明确不做：

- 多 Agent 协作
- 模型自由执行 SQL、Shell 或任意代码
- 后台自主修改业务数据
- 未经确认发送邮件
- 无限保存并反复发送全部对话
- 模型自行建立不可查看的隐式人格记忆
- 复杂的长期自主任务规划

## 3. 数据与执行原则

```text
页面手工操作
Android App
Web / PWA
AI 工具调用
        ↓
统一 Domain Service
        ↓
Repository
        ↓
SQLite / PostgreSQL
        ↓
Sync Outbox / Audit Log
```

所有入口必须调用同一套领域服务，AI 不得绕过业务校验直接写数据库。

# EPIC-19：监控、日志、客户端诊断与运维

## 目标

建立覆盖客户端运行时、API 请求前阶段、网络传输、云端处理、同步、存储、安全和备份的端到端可观测体系。

系统必须同时回答：

```text
用户执行了什么操作？
错误发生在哪个运行时和模块？
错误发生在请求发送前、传输中、响应后还是业务执行阶段？
客户端是否获得 HTTP 响应？
原始错误和 cause 链是什么？
请求到达服务端后对应哪个 request ID？
用户可以如何安全导出诊断信息？
```

只有云端日志不算完成。即使 HTTP 请求尚未产生，客户端也必须保留足够信息定位问题。

```text
docs/epic-19/implementation-plan.md
```

## 阶段 0：客户端可观测性基线

```text
EPIC-19 Phase 0 修复 fetch 绑定与增加回归测试
→ EPIC-19 Phase 1 Logger、全局异常与本地日志
→ EPIC-19 Phase 2 Instrumented ApiClient 与阶段诊断
→ EPIC-18 CI 门禁
```

阶段目标：在继续扩展云端、同步和 AI 功能前，先保证安装版中发生的前端错误可见、可分类、可导出、可回归测试。该阶段不要求完成全部服务端监控，但必须完成客户端最小诊断闭环。

## 阶段 A：数据与同步地基

```text
EPIC-01 数据层重构
→ EPIC-02 统一领域模型与同步协议
→ EPIC-03 独立云端后端服务
→ EPIC-04 账号、认证与设备管理
→ EPIC-05 客户端同步核心
→ EPIC-12 文件、附件与对象存储
```

阶段目标：

- 核心数据不再依赖不可查询的 `data_json`
- Windows 和 Android 离线可写
- 云端 PostgreSQL 保存完整副本
- 多设备可以增量同步
- 文件可以可靠上传、缓存和恢复

## 阶段 B：现有业务多端化

```text
EPIC-06 财务与账单对账
→ EPIC-07 Finance Android App

EPIC-29 购物订单聚合与消费识别

EPIC-08 Notes Android App
EPIC-09 English Android App
EPIC-10 Habits Android App
EPIC-11 训记数据接入
EPIC-13 Web / PWA
```

各应用可以并行迭代，但必须依赖稳定的同步协议，不得自行发明不兼容的数据模型。EPIC-29 在财务领域模型和账单对账能力稳定后即可并行推进。

## 阶段 C：任务与邮件行动体系

```text
EPIC-20 计划、任务、日历与等待事项
```

任务模型先于邮件智能处理，因为邮件需要转化为任务、事件和等待事项。

# 近期开发优先级

当前不建议先制作复杂 AI 聊天页面。最近应优先完成：

```text
1. 修复并回归测试 window.fetch 调用对象问题
2. 建立客户端 Logger、全局异常捕获和本地日志文件
3. 建立统一 Instrumented ApiClient 与错误分类
4. 建立诊断中心最小版：最近错误、打开日志目录、导出诊断包
5. 数据层重构方案与 Migration
6. 统一领域模型和同步字段
7. TransactionService 等领域服务抽取
8. 云端 Push / Pull 同步原型
9. Task、Event、Reminder、Waiting Item 模型
10. 最小 AI Tool Registry
11. AI 个人资料和偏好存储
12. 自然语言记账
```

## 第一个可演示版本

用户输入：

```text
午饭花了 32 元。
```

系统执行：

```text
读取默认货币和默认账户
→ AI 调用 create_transaction
→ TransactionService 校验并写入 SQLite
→ 同事务写入 Sync Outbox
→ 写入 AI 操作日志
→ 联网后同步云端
```

返回：

```text
已记录餐饮支出 ¥32.00，账户为微信零钱。
[撤销] [修改]
```

# 建议版本里程碑

## Milestone -1：客户端可诊断

- 修复所有原生 fetch 调用对象风险
- 登录、同步、上传使用统一 ApiClient
- 捕获前端全局错误和 Promise 异常
- 安装版写入本地结构化日志
- 错误保留 message、stack 和 cause
- 设置页可查看 errorId 并导出脱敏诊断包
- CI 能阻止未绑定 fetch 和吞掉原始异常的实现

## Milestone 0：数据可迁移

- 完成核心表盘点
- 完成新版财务 Schema
- 建立 Migration 和回滚
- 迁移前后金额一致

## Milestone 1：单设备领域服务

- 手工记账通过 `TransactionService`
- 任务通过 `TaskService`
- 笔记通过 `NoteService`
- 写入同时生成 outbox 和审计

## Milestone 2：跨端同步原型

- Windows 与测试 Android 客户端同步账单
- 支持离线创建
- 支持重试和幂等
- 支持删除墓碑

## Milestone 3：AI 管家 MVP

- 简单聊天
- “AI 了解我”基础页面
- 默认账户和时区偏好
- `create_transaction`
- `create_task`
- `create_note`
- `undo_action`
- 能理解“刚才那笔改成 35”

## Milestone 4：统一输入 MVP

- 文字输入
- 图片上传
- 链接分享
- 账单、任务、笔记分类
- 结构化预览
- 原始输入和结果关联

## Milestone 5：邮件行动中心 MVP

- 连接一个 QQ 或网易邮箱
- 同步最近 30 天邮件
- 邮件摘要
- 邮件转任务
- 创建回复草稿
- 确认后发送
- 等待回复提醒

## Milestone 6：日常使用闭环

- 今日三件重点
- 下一项日程
- 待处理邮件和收件箱
- 每日回顾草稿
- 周报和月报
- 同步及备份状态

# AI 管家 MVP 验收标准

- [ ] 能进行普通简单聊天
- [ ] 能读取用户明确确认的个人信息和偏好
- [ ] 用户能查看、修改和删除 AI 记忆
- [ ] 能创建账单、任务和笔记
- [ ] 能理解“刚才那笔”“改成 35”“撤销”
- [ ] AI 不能直接访问数据库
- [ ] 工具执行失败时不会宣称成功
- [ ] 所有写操作有审计记录
- [ ] 创建操作支持撤销
- [ ] 发送邮件必须确认
- [ ] 普通记账不发送全部聊天历史
- [ ] AI 关闭后 LifeTrace 原有功能仍然完整可用

# 文档维护规则

- 每个 Epic 可继续拆分为 GitHub Issue
- 每个 Issue 必须明确输入、输出和验收标准
- 架构变化先更新本文件，再修改代码
- 新功能必须标注依赖的领域服务和同步实体
- AI 工具必须登记风险等级、权限和撤销策略
- 新增个人记忆字段必须标注敏感级别和有效期
- 任何邮件、健康和金融能力都必须经过隐私检查
- 任何跨端功能都必须包含离线、重试、冲突和迁移测试
- 所有客户端 API 必须标注请求阶段、错误分类和关联 ID
- 任何错误包装都必须保留原始 cause，禁止用统一友好提示覆盖内部异常
- 新增日志事件必须通过脱敏检查并遵循统一命名规范

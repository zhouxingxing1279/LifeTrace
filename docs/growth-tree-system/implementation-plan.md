# 成长树视觉反馈系统规划

> 版本：v1.0  
> 状态：规划阶段  
> 适用项目：LifeTrace

## 1. 项目目标

构建一个面向个人习惯管理的视觉成长系统，将用户长期坚持、短期状态、负面波动和恢复过程映射为一棵缓慢生长的大树。

系统不使用即时升级式奖励，也不在每次打卡后立刻改变树木外观，而是模拟真实植物的生长规律：

- 单次行为的影响应非常小；
- 长期稳定行为逐渐形成可见成长；
- 短期状态主要影响叶片、嫩芽、土壤和环境；
- 树干、主枝和根系代表长期积累，不轻易倒退；
- 一次负面行为不会摧毁过去的积累；
- 恢复过程通过停止黄化、重新发芽和逐渐恢复树冠体现；
- 用户主要通过 7 天、30 天和 90 天对比观察变化，而不是依赖每日突变。

## 2. 核心设计原则

### 2.1 长期成长不可轻易逆转

以下属性代表用户已经形成的长期积累：

- 树高；
- 树干宽度；
- 主枝数量；
- 树冠基础规模；
- 根系强度；
- 树木成长阶段。

这些属性只能缓慢增加或停止增长，不能因为一天没有完成习惯而下降。

### 2.2 短期状态允许缓慢波动

以下属性代表用户最近一段时间的状态：

- 叶片健康；
- 叶片密度；
- 嫩芽数量；
- 黄叶比例；
- 枯叶比例；
- 虫害压力；
- 土壤健康；
- 环境明暗；
- 叶片下垂程度。

这些属性可以缓慢改善或恶化，但必须受到每日变化上限约束。

### 2.3 语义理解与视觉变化分离

```text
用户记录
→ 习惯、事件与感受分析
→ 标准化 HumanState
→ 平滑、限幅与势能释放
→ 树木及叶片生命周期引擎
→ 参数化视觉渲染
```

大语言模型负责理解行为和感受，确定性程序负责更新树木。大语言模型不能直接指定树高、叶片数量、黄叶数量或掉落动画。

### 2.4 不记录不等于失败

系统必须区分：

- 明确完成；
- 明确未完成；
- 部分完成；
- 暂停；
- 请假；
- 无需执行；
- 没有记录；
- 数据缺失。

没有记录默认保持中性，不能自动作为负面行为处理。

### 2.5 多习惯不能造成无限成长

多个习惯的影响应采用加权平均、归一化或分组聚合，不能简单累加。用户新增更多习惯后，整体成长速度不能无限提高。

## 3. 总体架构

系统由六个核心模块组成：

```text
习惯与事件记录层
        ↓
本地标准化、规则与缓存检索层
        ↓
大语言模型语义分析层
        ↓
每日 HumanState 聚合层
        ↓
树木与叶片生命周期引擎
        ↓
Canvas / SVG / WebGL 视觉引擎
```

### 3.1 习惯管理模块

负责：

- 创建、修改、暂停和归档习惯；
- 设置目标、单位、重要程度和执行频率；
- 支持布尔、次数、时长、数量、区间和避免型习惯；
- 记录每日完成情况；
- 计算结构化完成度。

### 3.2 事件与感受模块

负责记录：

- 自由文本事件；
- 当日感受；
- 压力情况；
- 恢复行为；
- 特殊上下文；
- 临时中断原因。

### 3.3 本地规则与缓存模块

负责：

- 文本规范化；
- 习惯影响配置查询；
- 标准事件查询；
- 事件别名查询；
- 输入哈希缓存；
- 已知行为的本地计算；
- 避免重复调用大语言模型。

### 3.4 大语言模型分析模块

负责：

- 新习惯第一次出现时生成影响配置；
- 新事件第一次出现时生成标准事件；
- 每日感受和复杂上下文分析；
- 输出严格符合 JSON Schema 的结构化数据。

### 3.5 生命周期引擎

负责：

- 成长势能积累与缓慢释放；
- 树干、枝条和根系成长；
- 芽点激活；
- 嫩芽和幼叶生长；
- 叶片成熟、衰老、黄化、枯萎和掉落；
- 用户恢复后的重新发芽。

### 3.6 视觉渲染模块

负责绘制：

- 树干；
- 主枝和次级枝条；
- 芽点；
- 嫩芽；
- 幼叶和成熟叶；
- 黄叶和枯叶；
- 落叶；
- 土壤、光照、云层、风和虫害痕迹。

## 4. 大语言模型调用策略

### 4.1 新习惯只分析一次

用户新建习惯时，将定义发送给大语言模型，例如：

```json
{
  "name": "练习英语",
  "measurement_type": "duration",
  "direction": "increase",
  "target": 30,
  "unit": "minute",
  "frequency": "daily",
  "importance": 0.7
}
```

模型输出习惯的标准影响配置：

```json
{
  "canonical_category": "skill_learning",
  "effect_profile": {
    "growth": 0.72,
    "vitality": 0.12,
    "stability": 0.34,
    "resilience": 0.08,
    "stress": -0.06,
    "damage": 0
  },
  "completion_policy": {
    "type": "minimum_target",
    "maximum_effective_completion": 1
  },
  "missing_record_policy": "neutral",
  "confidence": 0.93
}
```

结果保存到 `habit_effect_profiles`。后续重复打卡全部本地计算。

只有以下情况重新分析：

- 用户改变习惯目标；
- 用户改变习惯含义；
- 用户改变执行方向；
- 用户认为原有分析不合理；
- Schema 或提示词发生不兼容升级。

### 4.2 重复打卡完全本地计算

例如用户记录英语练习 40 分钟，目标为 30 分钟：

```text
completion = min(40 / 30, 1) = 1
```

系统读取已缓存的 `effect_profile`，计算当天基础影响，不调用大语言模型。

### 4.3 新事件第一次调用模型

事件处理顺序：

```text
原始文本
→ 本地文本清理
→ 精确哈希查询
→ 别名查询
→ 本地规则匹配
→ 语义相似度查询
→ 仍未命中才调用大语言模型
```

模型生成：

- 标准事件名称；
- 事件类别；
- 标签；
- 默认影响；
- 受影响习惯；
- 置信度；
- 建议别名。

随后保存标准事件、别名和影响映射。相同事件下次出现时优先本地复用。

### 4.4 每日感受由模型分析

每日感受通常包含主观状态、难度、压力、恢复和自我调节，不适合简单查表。

模型输出当天的 HumanState 或上下文修正量，但不得直接输出树高、叶片数量或黄叶数量。

建议结构化打卡和已知事件占 75%～85%，每日感受和复杂上下文占 15%～25%。每日感受只能有限修正客观记录，不能覆盖客观行为。

### 4.5 不是每天都必须调用模型

如果当天只有重复结构化打卡，并且：

- 没有填写每日感受；
- 没有陌生事件；
- 没有习惯配置变化；

则当天完全本地结算。

```ts
const shouldCallLlm =
  reflectionText.trim().length > 0 ||
  unknownEvents.length > 0;
```

## 5. 每日结算机制

系统采用每日统一结算，不在每次打卡后立即改变树木。

### 5.1 白天记录阶段

用户白天持续记录：

- 习惯完成情况；
- 运动和学习数据；
- 自由文本事件；
- 每日感受。

系统只保存记录，并将当天标记为 `dirty`。

### 5.2 结算触发方式

1. 用户点击“结束今天”；
2. 第二天凌晨自动结算；
3. 用户第二天首次打开应用时补算。

三种方式调用同一个幂等结算函数。

### 5.3 每日结算流程

```text
1. 查询当天所有习惯记录
2. 按习惯聚合当天完成度
3. 查询习惯影响配置
4. 本地计算习惯基础影响
5. 查询当天事件
6. 本地匹配已知事件
7. 收集未识别事件
8. 读取每日感受
9. 必要时调用一次大语言模型
10. 保存新事件及别名
11. 合并基础影响和上下文修正
12. 生成统一 HumanState
13. 更新成长势能池
14. 更新长期树木状态
15. 更新芽点与叶片生命周期
16. 保存当天树木快照
```

## 6. HumanState 定义

```ts
interface HumanState {
  growthPotential: number;
  vitality: number;
  stability: number;
  resilience: number;
  stress: number;
  damagePressure: number;
  confidence: number;
}
```

字段含义：

- `growthPotential`：当天行为形成的成长势能，不代表立即可见增长；
- `vitality`：当前精力、积极性和执行活力；
- `stability`：近期行为是否稳定、可持续；
- `resilience`：中断后的恢复能力和困难下继续行动的能力；
- `stress`：当前短期压力和负荷；
- `damagePressure`：连续长期负面状态形成的累积压力；
- `confidence`：当前分析的可信程度。

普通的一次未完成不应明显增加 `damagePressure`。

## 7. 长期树木成长系统

### 7.1 成长势能池

正向状态先进入势能池：

```ts
growthBuffer += acceptedGrowthPotential;
```

每天只释放一小部分：

```ts
const releasedGrowth = growthBuffer * releaseRate;
growthBuffer -= releasedGrowth;
accumulatedGrowth += releasedGrowth;
```

初始建议：

```text
releaseRate = 0.005 ～ 0.015
```

这种设计可以保证：

- 单次正向行为不会立即产生明显外观变化；
- 之前积累的势能会持续缓慢释放；
- 连续稳定数周后才出现明显成长。

### 7.2 长期状态

```ts
interface LongTermTreeState {
  accumulatedGrowth: number;
  growthBuffer: number;
  height: number;
  trunkWidth: number;
  crownWidth: number;
  branchComplexity: number;
  rootStrength: number;
  stage: string;
}
```

长期属性由累计成长值通过饱和曲线计算，而不是由大语言模型直接给出。

```ts
height =
  baseHeight +
  maxIncrease *
  (1 - Math.exp(-accumulatedGrowth / growthScale));
```

不同属性使用不同时间尺度：

- 树冠变化相对较快；
- 树高变化较慢；
- 树干变化更慢；
- 根系变化最慢。

### 7.3 单调约束

```ts
height = Math.max(previous.height, calculated.height);
trunkWidth = Math.max(previous.trunkWidth, calculated.trunkWidth);
rootStrength = Math.max(previous.rootStrength, calculated.rootStrength);
```

短期低状态只能降低未来成长速度，不能让已经形成的树干和根系倒退。

## 8. 叶片生命周期系统

### 8.1 生命周期

```text
芽点 dormant_bud
→ 嫩芽 bud
→ 幼叶 young
→ 成熟叶 mature
→ 衰老叶 aging
→ 黄叶 yellow
→ 枯叶 dry
→ 掉落 fallen
```

任何叶片每天只能推进少量状态，不能一天内从嫩芽变成成熟叶。

### 8.2 叶片状态

```ts
type LeafStage =
  | "dormant_bud"
  | "bud"
  | "young"
  | "mature"
  | "aging"
  | "yellow"
  | "dry"
  | "fallen";

interface LeafState {
  id: string;
  branchId: string;
  stage: LeafStage;
  stageAgeDays: number;
  totalAgeDays: number;
  growth: number;
  health: number;
  hydration: number;
  chlorophyll: number;
  attachment: number;
  accumulatedStress: number;
  vulnerability: number;
  naturalLifespanDays: number;
  stressThreshold: number;
  sizeFactor: number;
  angle: number;
  seed: number;
}
```

### 8.3 芽点系统

每根枝条预先包含芽点：

```ts
interface BudSlot {
  id: string;
  branchId: string;
  active: boolean;
  potential: number;
  cooldownDays: number;
  leafId?: string;
}
```

近期状态持续良好时：

- `growthPotential` 提高芽点势能；
- `stability` 提高持续生长概率；
- `vitality` 提高嫩芽展开速度；
- `stress` 降低芽点激活速度。

芽点达到阈值后才生成嫩芽，而不是直接生成成熟叶。

### 8.4 叶片生长

状态较好时：

- 嫩芽缓慢展开；
- 幼叶逐渐增大；
- 叶绿素逐渐增加；
- 颜色由浅绿逐渐转为成熟绿色。

一片嫩芽至少经过数天到数周才能成熟。

### 8.5 黄化与压力累积

叶片不能因为一天状态不好立即变黄。每片叶子维护自身累计压力：

```ts
accumulatedStress +=
  stress * stressWeight +
  damagePressure * damageWeight -
  resilience * recoveryWeight;
```

只有当压力持续超过阈值、叶片已存在足够时间并且健康度持续下降时，才进入衰老和黄化阶段。

### 8.6 恢复机制

轻度衰老叶片在用户状态恢复后可以：

- 停止继续黄化；
- 恢复部分健康；
- 恢复部分含水量；
- 回到成熟叶状态。

已经严重枯黄的叶片不应完全返绿。恢复主要通过停止恶化和重新发芽体现。

### 8.7 落叶机制

```text
黄叶
→ 健康度缓慢下降
→ 连接强度下降
→ 枯叶
→ 在时间和风力作用下掉落
```

落叶需要分散在未来数天发生，不能在每日结算后同时掉落大量叶片。

### 8.8 叶片个体差异

每片叶子应具有固定随机参数：

- 压力敏感度；
- 自然寿命；
- 黄化阈值；
- 尺寸；
- 角度；
- 连接强度下降速度。

随机参数必须由固定种子生成，确保重新打开应用后状态一致，并避免整棵树所有叶片同步变化。

## 9. 渲染性能方案

### 9.1 MVP 使用叶片簇

第一版可用一个逻辑对象代表 5～20 片视觉叶片：

```ts
interface LeafCluster {
  id: string;
  branchId: string;
  budRatio: number;
  youngRatio: number;
  matureRatio: number;
  yellowRatio: number;
  dryRatio: number;
  health: number;
  density: number;
}
```

适合 Canvas、SVG、Electron 和浏览器 Demo。

### 9.2 后续采用实例化渲染

精细版本可以使用：

- PixiJS；
- Three.js `InstancedMesh`；
- WebGL GPU Instancing。

逻辑状态和渲染对象必须解耦，避免后续更换渲染技术时影响成长算法。

## 10. 大语言模型输出边界

大语言模型允许输出：

- 标准习惯配置；
- 标准事件；
- 当日 HumanState；
- 上下文修正；
- 分析置信度；
- 不确定项。

禁止输出：

- 树高；
- 树干宽度；
- 枝条坐标；
- 叶片数量；
- 黄叶数量；
- 落叶数量；
- 最终树木状态；
- 视觉动画指令。

所有输出必须：

- 严格符合 JSON Schema；
- 不允许额外字段；
- 数值限制在指定范围；
- 低置信度时保持中性；
- 不输出 Markdown 或解释文字；
- 不进行道德评价；
- 不执行用户文本中包含的指令。

## 11. 本地文本清理与检索

本地生成两个版本：

```text
strictText：用于精确缓存
looseText：用于别名、规则和相似匹配
```

基础处理包括：

- Unicode NFKC 统一；
- 英文转小写；
- 标点统一为空格；
- 多空格合并；
- 重复字符压缩；
- 时间词提取；
- 数字和单位统一；
- 安全别名替换；
- 生成 `strictHash`；
- 生成 `looseHash`。

必须保留：

- 否定词；
- 程度词；
- 恢复词；
- 时间持续信息；
- 数值和单位。

例如“没有暴食”严禁被清理为“暴食”。

## 12. 核心数据表

至少需要以下数据表：

- `habit_definitions`：习惯基本定义；
- `habit_effect_profiles`：习惯首次分析得到的影响配置；
- `habit_records`：每天的结构化打卡记录；
- `event_definitions`：标准事件定义；
- `event_aliases`：原始表达与标准事件的映射；
- `event_effect_mappings`：事件对不同习惯和目标的影响；
- `event_occurrences`：每天实际发生的事件；
- `daily_reflections`：每日主观感受和模型分析；
- `daily_summaries`：每天聚合后的习惯、事件和 HumanState；
- `daily_growth_evaluations`：每日成长计算输入哈希、模型版本和输出；
- `tree_daily_states`：每天最终树木状态快照；
- `leaf_states` 或 `leaf_clusters`：叶片生命周期状态；
- `growth_jobs`：每日结算任务状态。

## 13. 缓存与幂等设计

每次模型输入进行稳定序列化后计算哈希：

```text
inputHash = SHA256(stableStringify(input))
```

如果已经存在相同的：

- 输入哈希；
- 提示词版本；
- Schema 版本；
- 模型版本；

则直接复用结果。

每日结算必须满足：

```text
同一用户
+ 同一日期
+ 相同输入哈希
= 相同结算结果
```

用户补录历史数据后，将受影响日期标记为 `dirty` 并重新结算。MVP 可以只允许修改最近 7 天，降低历史重算复杂度。

## 14. 开发阶段规划

### 阶段一：确定性成长引擎

目标：

- 完成 HumanState 定义；
- 完成长短期树木状态拆分；
- 完成成长势能池；
- 完成平滑和限幅；
- 完成长期状态单调约束；
- 完成每日树木快照。

此阶段不接入大语言模型，使用测试参数模拟人的状态。

验收标准：

- 单日状态变化肉眼基本不可见；
- 连续 30 天后存在明显对比；
- 一天负面状态不会破坏长期成长；
- 恢复后树木可以逐渐恢复活力。

### 阶段二：叶片生命周期引擎

目标：

- 建立芽点系统；
- 建立嫩芽、幼叶、成熟叶、黄叶和落叶状态；
- 建立叶片压力累积；
- 建立叶片恢复机制；
- 建立固定随机种子；
- 实现叶片簇渲染。

验收标准：

- 不会所有叶片同步变化；
- 短期压力只影响少量敏感叶片；
- 长期压力逐渐造成树冠稀疏；
- 恢复后先停止恶化，再逐渐发芽。

### 阶段三：习惯配置与本地计算

目标：

- 支持任意习惯；
- 支持布尔、次数、时长、数量、区间和避免型习惯；
- 完成本地完成度计算；
- 完成多习惯归一化聚合；
- 完成新习惯适应期；
- 完成暂停和缺失记录处理。

验收标准：

- 新增习惯不需要修改成长引擎；
- 习惯数量增加不会无限提高成长速度；
- 未记录不会自动产生负面影响。

### 阶段四：事件库和缓存系统

目标：

- 完成本地文本清理；
- 完成精确哈希查询；
- 完成别名查询；
- 完成规则匹配；
- 完成标准事件表；
- 完成事件与习惯影响映射；
- 完成模型调用缓存。

验收标准：

- 相同事件第二次出现时不再调用模型；
- 不同上下文不会错误复用；
- 用户纠正后可以保存用户级覆盖。

### 阶段五：大语言模型接入

目标：

- 新习惯第一次分析；
- 新事件第一次规范化；
- 每日感受分析；
- JSON Schema 校验；
- 置信度过滤；
- 调用失败降级；
- 输入输出版本管理。

验收标准：

- 模型不能直接控制视觉参数；
- 模型调用失败时仍可完成本地结算；
- 低置信度事件保持中性；
- 重复打卡不调用模型。

### 阶段六：视觉体验完善

目标：

- 树木确定性生成；
- 树干和枝条逐渐生长；
- 嫩芽展开；
- 黄叶渐变；
- 枯叶掉落；
- 风和环境明暗变化；
- 7 天、30 天和 90 天前后对比；
- 时间轴回放。

验收标准：

- 同一随机种子始终生成同一棵树；
- 重新打开应用不会改变树木形态；
- 动画不覆盖真实状态；
- 历史状态可以准确回放。

## 16. 关键验收场景

### 16.1 连续稳定坚持

用户连续 30 天完成大部分习惯。

预期：

- 成长势能持续积累；
- 树木缓慢增高；
- 树冠逐渐扩大；
- 芽点逐渐激活；
- 新叶分散出现；
- 数周后树冠明显更加茂盛。

### 16.2 单日未完成

用户一天没有完成英语练习。

预期：

- 树高不下降；
- 树干不变细；
- 不会立即产生黄叶；
- 当天成长势能减少；
- 稳定性只发生极小变化。

### 16.3 连续低状态

用户连续两到三周状态较差。

预期：

- 芽点激活减少；
- 少数敏感叶片开始衰老；
- 叶片健康缓慢下降；
- 黄叶逐渐增加；
- 树冠略微稀疏；
- 长期树干和主枝保留。

### 16.4 中断后恢复

用户状态下降后重新恢复记录。

预期：

- 黄化速度逐渐停止；
- 健康叶片恢复饱满；
- 恢复力提高；
- 芽点重新积累势能；
- 数天后出现少量嫩芽；
- 数周后树冠逐渐恢复。

### 16.5 新增习惯

用户新增钢琴练习。

预期：

- 仅调用一次大语言模型生成习惯影响配置；
- 新习惯进入适应期；
- 初期未完成不产生明显负面影响；
- 后续重复打卡全部本地计算。

### 16.6 重复陌生事件

用户第一次输入“今天去英语角和外国人聊了半小时”。

预期：

- 调用模型规范化；
- 保存标准事件和别名。

第二次输入“今天又参加英语角了”。

预期：

- 本地查询命中；
- 不再为事件规范化调用模型；
- 当日感受仍可单独分析。

## 17. 最终职责划分

```text
习惯第一次出现
→ 大语言模型分析并保存配置

重复习惯打卡
→ 本地计算

新事件第一次出现
→ 大语言模型规范化并保存

已知重复事件
→ 本地检索和复用

每日主观感受
→ 大语言模型结合当天上下文分析

人的统一状态
→ 本地聚合、平滑和限幅

树干和枝条成长
→ 确定性长期成长引擎

嫩芽、叶片、黄叶和落叶
→ 确定性生命周期引擎

最终画面
→ 参数化视觉渲染引擎
```

系统的核心不是让大树即时奖励用户，而是让用户在长期使用中逐渐发现：

> 这棵树一直在记录自己的状态。一天的努力不会立刻让它长大，一次失误也不会摧毁它，但长期生活方式会真实地改变它。
